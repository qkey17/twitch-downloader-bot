# Обновление существующего стенда до PR #4 / 75d1654

**Команды ниже подготовлены, но обновление вашей VM и systemd-прогон ещё не выполнены.**
Переход поддерживает только установку c77b5f7 (контроллер 0a9a453) → контроллер
`75d16545c5ccbdb965b7dfd2cd73dd605f6f2e0d`. Нужны исходные, не отредактированные файлы.
Для старых Windows bundles разрешены только известные LF/CRLF варианты кода.

Это инструкция для сопровождения **по одной команде за раз**: выполнить команду,
проверить указанный результат, только затем перейти дальше. При любом другом результате
остановиться и сохранить текст ошибки. Не повторять тесты ради PASS и не увеличивать тайм-ауты.

## 1. Подготовить и выключить только гостевую Ubuntu

Все три команды — **в работающей последовательной консоли Ubuntu внутри QEMU**, не в Windows.

```sh
sudo python3 -I -S -B /var/lib/tdb-harness/code/guest.py check
```

Ожидается `ISOLATED_GUEST_OK`.

```sh
sudo python3 -I -S -B /var/lib/tdb-harness/code/guest.py cleanup
```

Ожидается `CLEANUP_OK`. Эта существующая процедура останавливает только тестовые
службы и отключает их автоматический запуск. Старые cases и отчёты сохраняются.
Не продолжать при активных units/jobs, ошибке cleanup или незавершённом powercut.

```sh
sudo poweroff
```

Ожидается штатное завершение **только гостя** и возврат в Windows CMD. Дождаться
полного выхода QEMU. Не выключать Windows и не применять команды к Oracle.

## 2. Получить проверенный комплект в Windows CMD

Команды — **в Windows CMD**. Нужен обычный CMD, права администратора Windows не требуются.

```bat
cd /d C:\TCD-Systemd-Test\repo
```

Ожидается приглашение `C:\TCD-Systemd-Test\repo>`.

```bat
git branch --show-current
```

Ожидается `codex/systemd-integration-harness`. При другой ветке остановиться,
не переключать её с отбрасыванием изменений.

```bat
git pull --ff-only
```

Ожидается успешное обновление. Если Git сообщает о локальных изменениях — сохранить
их и остановиться, не использовать reset/force. Сверить полученный SHA с SHA из отчёта
к этой задаче; при необходимости следующим отдельным шагом выполнить `git rev-parse HEAD`.

```bat
git fetch origin codex/daily-maintenance-backup
```

Ожидается успешное получение Git-объектов PR #4. Ветка PR #4 при этом не меняется.
Сеть используется только Windows Git, никогда внутри guest.

```bat
tests\systemd_harness\update.cmd build
```

Ожидаются `ISO_READY`, `ISO_SHA256`, `SOURCE 75d16545... HARNESS <полный SHA>`.
Полный HARNESS SHA должен совпадать с проверенным коммитом этой задачи.
Скрипт проверяет Git и Python 3.12+, ничего не устанавливает. Экспортируются только
allowlisted файлы из зафиксированных Git-коммитов, не из изменённого checkout.
Контроллер/backup/maintenance берутся из точного 75d1654 и сверяются с заранее
известными SHA-256. У dirty checkout сборка откажет.

ISO9660 создаётся средствами Python, без xorriso/oscdimg/PowerShell COM и скачивания
пакетов. Новый каталог bundle и ISO имеют уникальное имя `tdb-update-75d1654-<id>`
в `C:\TCD-Systemd-Test`. Старый `tdb-harness-reset-fix.iso` не перезаписывается.
Последний подготовленный ISO и его checksum записываются в `repo\_work\update-iso.json`.

```bat
tests\systemd_harness\update.cmd run
```

Ожидается запуск прежней Ubuntu с последовательной консолью. Скрипт повторно проверит
checksum ISO, наличие `vm\vm.json`, `vm\guest.qcow2` и QEMU в PATH либо
`C:\Program Files\qemu`. VM и диск **не создаются заново**. Используются прежний UUID,
954 МиБ/1 vCPU/TCG, без NIC, общих каталогов и host bus. ISO подключается read-only.
При занятом qcow2 остановиться: не запускать вторую VM и не отключать блокировку диска.

## 3. Обновить код внутри прежней Ubuntu

Далее команды — **в последовательной консоли Ubuntu**, вставляются обычными однострочными командами.

```sh
sudo mkdir -p /mnt/tdb75
```

Ожидается завершение без ошибки.

```sh
sudo mount -o ro,map=normal /dev/sr0 /mnt/tdb75
```

Ожидается смонтированный read-only ISO. `map=normal` обеспечивает нижний регистр
ASCII имён ISO9660 ([документация Linux](https://www.kernel.org/doc/html/latest/filesystems/isofs.html)).
Никакие host directories не монтируются.

```sh
sudo python3 -I -S -B /mnt/tdb75/update.py apply
```

Ожидается `UPDATE_VERIFIED base=75d16545c5ccbdb965b7dfd2cd73dd605f6f2e0d harness=<SHA>`.
Updater самостоятельно проверяет среду, manifest/checksums, старые файлы, аттестацию,
владельцев/права, остановленные units/jobs и отсутствие тестовых процессов, в том
числе вне unit. Он **не** вызывает start/stop/reset/enable/mask и не изменяет units.
Обе копии контроллера заменяются и проверяются:

- `/var/lib/tdb-harness/code/tools/daily_backup.py`;
- `/var/lib/tdb-harness/admin/daily_backup.py`.

```sh
sudo python3 -I -S -B /var/lib/tdb-harness/code/update.py verify
```

Ожидается такой же `UPDATE_VERIFIED` с правильным BASE и HARNESS. Проверяются все
установленные модули, обе копии контроллера, wrappers и сохранённая аттестация.
Не повторять `provision`, не редактировать код вручную, не удалять старые данные.

## Ошибка или прерывание именно обновления

Updater хранит резервные копии только разрешённых файлов кода и журнал в
`/var/lib/tdb-harness/updates/<id>`. `guest.json` остаётся побайтно прежним;
`version.json` отдельно фиксирует обновление. Cases, SQLite, HTML, прежние отчёты,
current config и журналы не копируются и не изменяются.

Обычная ошибка копирования вызывает проверяемый откат. При SIGKILL/потере питания
остаётся journal=`applying`, и новый guard блокирует обычные команды стенда.
Изоляционные проверки всегда действуют; только updater может пройти этот запрет,
чтобы закончить восстановление. Публичный root-owned `update-status.json` содержит
лишь ID/статус для непривилегированного `tdbh`; backup/journal остаются root-only.
При откате старый guard возвращается последним. Рекурсивных удалений нет.

После перезапуска подключить тот же ISO и повторить команду mount из шага 3, затем:

```sh
sudo python3 -I -S -B /mnt/tdb75/update.py recover
```

Ожидается `ROLLBACK_OK`: исходные файлы восстановлены, данные сохранены. При
повторном прерывании recovery её можно повторить. Не удалять update journal/backup.
Если неизвестный файл или повреждённая backup-копия мешает rollback — остановиться,
сохранить VM и диагностику. Не обходить checksums. После подтверждённого rollback
можно снова выполнить `apply`; он создаст отдельную новую транзакцию.

Если операция успела зафиксировать все файлы, но потеряла последний публичный маркер,
`recover` откажет для committed-транзакции. Тогда отдельной командой выполнить
`/mnt/tdb75/update.py verify` с теми же `sudo python3 -I -S -B`: полная проверка
завершит только маркер статуса. Это не повторный прогон тестов и не изменение кода.

Локальные Windows-тесты используют синтетические файлы и ответы manager. POSIX
ownership/chown и ctime моделируются отдельно. Они не подтверждают реальный mount
ISO9660, фактическую замену внутри Ubuntu или прохождение systemd-сценариев.
Root, намеренно меняющий metadata/код или обходящий процедуру, вне модели защиты.

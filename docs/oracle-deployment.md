# Ручное обновление Oracle VM через GitHub Actions

Этот workflow обновляет существующий бот, а не устанавливает новый сервер.
Он подготовлен для `ubuntu@129.153.145.173`, checkout
`/home/ubuntu/twitch-downloader-bot`, `.venv` и `tdb.service`.
Ничего из описанного ниже не выполнено автоматически при подготовке файлов.

## Что делает автоматизация

- Только `workflow_dispatch`, без запуска на push. Запускать из ветки `main`.
- По умолчанию `check_only=true`: проверяет SSH, checkout, службу, окружение
  и разрешения. Не обновляет код и не перезапускает бот. Создаёт только
  приватный каталог/файл блокировки помощника, если их ещё нет.
  GitHub deployment-объект для такой проверки не создаётся.
- Пустой `commit` означает полный `GITHUB_SHA` выбранной версии `main` на момент
  запуска workflow. Можно указать другой полный SHA из истории `main`.
  Перемещение `main` после запуска не изменяет выбранный коммит.
- Сервер делает fetch и проверяет принадлежность SHA `origin/main`, чистоту
  отслеживаемых файлов и возможность fast-forward от текущего HEAD. Откат и
  расхождение веток запрещены. Обновление выполняется `merge --ff-only SHA`,
  без `pull`, который мог бы выбрать более новый коммит.
- Остановка штатная: SIGTERM, ожидание завершения задач до 10 минут, без
  принудительного убийства. Если бот не остановился, код не обновляется,
  в systemd ставится запрос запуска после окончания остановки, run завершается
  ошибкой. Не запускайте второй процесс бота вручную.
- После обновления проверяются синтаксис и импорт `src.main`, затем запуск
  службы. За 180 секунд должны появиться `active/running`, новый InvocationID
  и сообщение логгера `telegram.ext.Application` о старте именно этой
  systemd-инстанции и её основного PID, в штатном формате логов проекта.
  Ещё 10 секунд проверяется отсутствие остановки/перезапуска, тот же PID и SHA.
- Только после этих проверок помощник подтверждает `DEPLOYED <SHA>`, а workflow
  пишет `Deployment verified`. Успех preflight не означает развёртывание.

GitHub concurrency и серверный `flock` исключают параллельные запуски этого
помощника. Незавершённый run не отменяется следующим. GitHub может заменить
старый ожидающий run новым; не считайте это очередью гарантированных обновлений.
Все ручные обновления также нужно проводить этим помощником: прежняя команда
`stop; pull; start` не использует его блокировку.

## Сохранность данных и ограничения

Помощник не читает и не переписывает `.env`, не удаляет SQLite, HTML или
пользовательские файлы, не выполняет reset/clean/checkout и не устанавливает
пакеты в `.venv`. Дополнительно запрещены защищённые пути в выбранном Git-дереве
и среди всех изменений, включая удаления. Новые отслеживаемые файлы не должны
совпадать с существующими локальными или проходить через локальные symlink.
Git merge получает `--no-overwrite-ignore`, чтобы не перезаписывать игнорируемые
файлы. Ошибка чтения состояния или списка путей вызывает отказ, а не считается
пустым успешным ответом. Приватный временный список путей удаляется при выходе.
Изменённые tracked-файлы на сервере приводят к отказу до остановки.

Обновления `requirements.txt` и `src/database/` намеренно отклоняются. Для них
нужен отдельный план обслуживания, проверки совместимости и резервные копии.
Если зависимости прежние, используется существующая `.venv`, проверяемая через
`pip check`. Будущие новые импорты без объявленных зависимостей всё равно могут
потребовать ручного обслуживания.

Перед первым применением и перед релизами, затрагивающими данные, сделайте
проверенные резервные копии SQLite и HTML. Автоматизация не восстанавливает
старую базу и не откатывает код: после старта приложение может выполнять своё
существующее восстановление реестра и очистку HTML при нехватке диска.
Эти механизмы автоматизация не меняет и не отменяет.

При ошибке после запроса остановки EXIT/HUP/INT/TERM-обработчик проверяет,
что checkout чист и HEAD соответствует прежнему или выбранному SHA. Только
тогда он пытается поставить запуск `tdb.service` в очередь, сохраняя ошибочный статус workflow.
При незавершённом/частичном изменении checkout автоматический запуск запрещён.
До обновления это прежний код; после обновления — выбранный код. Не обещается
автоматический возврат к прежней версии. При повреждённом checkout, ошибке
нового кода, SIGKILL, выключении VM или отказе systemd восстановление требует
администратора. Запрос восстановления запуска не равен подтверждённому запуску.

## Однократная подготовка VM

Выполните через свой обычный административный доступ, не через будущий ключ CI.
Не меняйте и не копируйте credentials в репозиторий.

1. Проверьте наличие Bash, Git, OpenSSH, `flock` (Ubuntu `util-linux`), `timeout`
   (coreutils), Python 3.12 и рабочей `.venv`. Checkout должен принадлежать
   ожидаемому репозиторию и находиться на `main`. Для приватного репозитория
   отдельно настройте серверу read-only доступ GitHub; не используйте ключ
   Actions → Oracle для направления Oracle → GitHub. Fetch не должен спрашивать
   пароль. В origin не должно быть URL с токеном.
2. Передайте проверенный `deploy/oracle_deploy.sh` на VM своим обычным доступом,
   например во временный `/tmp/tdb-deploy`, затем установите root-owned копию:

   ```sh
   sudo install -d -o root -g root -m 0755 /usr/local/libexec
   sudo install -o root -g root -m 0755 /tmp/tdb-deploy /usr/local/libexec/tdb-deploy
   rm -- /tmp/tdb-deploy
   ```

   Не запускайте обновление кода через `sudo`: помощник обновляет checkout как
   `ubuntu`. Root разрешён только для фиксированной проверки `ready`, которая
   ничего не печатает из журнала. Установленная копия не обновляется из Git
   автоматически; изменение помощника требует повторной ручной проверки и установки.
3. Проверьте `WorkingDirectory=/home/ubuntu/twitch-downloader-bot` и запуск
   `/home/ubuntu/twitch-downloader-bot/.venv/bin/python -m src.main` в
   существующем unit. Не заменяйте EnvironmentFile и другие рабочие настройки.
   При необходимости добавьте через `sudo systemctl edit tdb.service`:

   ```ini
   [Service]
   Type=simple
   KillSignal=SIGTERM
   KillMode=control-group
   SendSIGKILL=no
   TimeoutStopSec=infinity
   StandardOutput=journal
   StandardError=journal
   ```

   Затем `sudo systemctl daemon-reload`. Не требуется перезапуск только ради
   установки помощника. Для будущего запуска задайте `TCD_LOG_LEVEL=INFO` в
   существующем EnvironmentFile: при WARNING/ERROR сообщение PTB о старте
   отсутствует, и автоматизация правильно откажется подтверждать готовность.
   Первую остановку/проверку этой конфигурации наблюдайте вручную.
4. Через `sudo visudo -f /etc/sudoers.d/tdb-deploy` разрешите только нужные
   команды, проверьте синтаксис `sudo visudo -cf /etc/sudoers.d/tdb-deploy`:

   ```sudoers
   Cmnd_Alias TDB_DEPLOY = /usr/bin/systemctl --no-block stop tdb.service, /usr/bin/systemctl --no-block start tdb.service, /usr/local/libexec/tdb-deploy ready
   ubuntu ALL=(root) NOPASSWD: TDB_DEPLOY
   ```

   Это не отменяет уже существующие административные разрешения `ubuntu`.
   Ограничение отдельного SSH-ключа обеспечивается также forced command ниже.
   Возможность развёртывать код, исполняемый как `ubuntu`, остаётся привилегией
   доверенных сопровождающих репозитория, а не изоляцией от вредоносного кода main.

## Отдельный ключ и проверка сервера

На доверенном компьютере создайте отдельный ключ, не используя существующий
приватный административный ключ:

```sh
ssh-keygen -t ed25519 -f ~/.ssh/tdb_actions -C tdb-github-actions
```

Для этого автоматизированного ключа оставьте passphrase пустой. Приватную часть
храните только в защищённом локальном месте и GitHub Environment Secret;
не добавляйте её ни в Git, ни в файлы workflow, ни в логи.

В `/home/ubuntu/.ssh/authorized_keys` **добавьте**, не заменяя другие ключи:

```text
restrict,command="/usr/local/libexec/tdb-deploy" ssh-ed25519 <PUBLIC_KEY> tdb-github-actions
```

Замените `<PUBLIC_KEY>` публичной частью нового ключа. Каталог `.ssh` должен
иметь режим 0700, authorized_keys — 0600, владельца `ubuntu`. Для этого ключа
запрещены shell/PTY, перенаправления портов и агента; разрешены только команды
`check` и `deploy <полный SHA>`, которые разбирает установленный помощник.
Не ослабляйте права существующих ключей и не меняйте их содержимое.
Убедитесь, что sshd не разрешает этому пользователю задавать произвольное
окружение: сохраните `PermitUserEnvironment no`, не разрешайте через `AcceptEnv`
переменные вроде `BASH_ENV`, `ENV`, `PATH`, `LD_*` и `GIT_*`. Forced command
не должен запускаться через подконтрольный клиенту файл инициализации shell.

Получите host key через доверенную консоль Oracle или уже проверенное
административное соединение, сверив fingerprint независимо:

```sh
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
sudo awk '{print "129.153.145.173 " $1 " " $2}' /etc/ssh/ssh_host_ed25519_key.pub
```

Вторая команда выдаёт публичную строку known_hosts. Сохраните её в соответствующий
Secret после проверки fingerprint. Не используйте слепой ssh-keyscan из Actions
как подтверждение личности сервера. При смене host key обновляйте pin только
после независимой проверки, а не отключайте StrictHostKeyChecking.

## GitHub и сеть

В `qkey17/twitch-downloader-bot` создайте Environment **oracle-production**:

- Deployment branches: только `main`.
- По возможности включите required reviewers; доступность зависит от тарифа и
  видимости репозитория. Ограничьте права запуска/изменения workflow доверенными людьми.
- Environment Secrets:
  - **ORACLE_SSH_PRIVATE_KEY** — полное содержимое нового приватного ключа.
  - **ORACLE_SSH_KNOWN_HOSTS** — проверенная публичная строка host key сервера.

Telegram/Twitch credentials сюда переносить не нужно: они остаются на VM.
Проверьте, что Oracle NSG/security list и локальный firewall допускают TCP/22 от
выбранного runner. У обычного GitHub-hosted runner нет одного постоянного
исходящего IP. Не открывайте SSH всему Интернету только ради автоматизации;
если действующая сетевая политика не допускает hosted runners, сначала отдельно
организуйте runner с разрешённым постоянным исходящим адресом/доверенным маршрутом.
Сам workflow такую сетевую настройку не создаёт.

## Проверка и запуск

Workflow должен находиться на `main`, чтобы появилась кнопка ручного запуска.
Публикация файлов в Git сама по себе не запускает развёртывание.

1. Actions → **Oracle deployment** → Run workflow → Branch `main`.
   Сначала оставьте **check_only=true**. Успех должен явно сообщать
   `Preflight passed. No code update or service restart was performed.`
2. После проверки доступа, резервных копий и выбранного релиза снимите
   `check_only`. Укажите полный SHA коммита из `main` либо оставьте поле пустым.
3. Успех: зелёный run, summary `Deployment verified` с точным SHA. Это означает
   активную новую инстанцию с подтверждённым `Application started`, но не заменяет
   функциональную проверку команды бота в Telegram.
4. При ошибке смотрите имя этапа и безопасные поля состояния в Actions. Полный
   журнал намеренно туда не копируется: он может содержать токены и пользовательские
   данные. С административного SSH проверьте на VM:

   ```sh
   cd /home/ubuntu/twitch-downloader-bot
   git rev-parse HEAD
   git status --short
   sudo systemctl is-active tdb.service
   sudo journalctl -u tdb.service --since '10 minutes ago' --no-pager
   ```

   Не публикуйте сырой журнал. Если служба не восстановилась, администратор
   проверяет checkout/данные и запускает её вручную после устранения причины.
   Откат кода или SQLite — отдельное решение с проверкой совместимости.

Основания выбранных механизмов: [GitHub deployment/concurrency](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/control-deployments),
[OpenSSH authorized_keys](https://man.openbsd.org/sshd.8),
[Git merge: защита игнорируемых файлов](https://git-scm.com/docs/git-merge),
[systemd invocation fields](https://www.freedesktop.org/software/systemd/man/251/systemd.journal-fields.html).

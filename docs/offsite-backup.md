# Отправка готовой копии в Dropbox

`tools/offsite_backup.py` отправляет **уже завершённый** каталог `tdb-backup-v1` без изменения его содержимого. Он повторно использует `backup_restore.verify_backup`, потоково передаёт `tar.gz` в age и сохраняет только зашифрованный файл. Приложение, `.env`, production SQLite/HTML и systemd не используются. Для этой отправки остановка бота не требуется; создание согласованного исходного snapshot остаётся отдельной [maintenance-процедурой](backup-restore.md).

## Подготовка

- Python 3.12+, age 1.1.1+, rclone 1.60.1+ в `PATH`; дополнительных Python packages нет. Передавайте оба проверенных файла `offsite_backup.py` и `backup_restore.py` рядом в отдельный административный каталог. Обновление production checkout не требуется.
- Используется существующий прямой Dropbox remote `tdb-dropbox`, каталог `tdb-dropbox:TCD-Backups`. Alias/crypt backend, shared-files/shared-folders и root аккаунта не поддерживаются. У remote должны работать чтение, запись, quota, server-side Move и удаление отдельных файлов. `dry-run` проверяет план, но не доказывает разрешение записи: окончательный ответ даёт Dropbox при upload.
- На Oracle нужен **только открытый age recipient**, уже установленный default: `age1afe9mj8gqgvtxm0e9cla8e2pmcj238nthcrfr5drmv45c29qd5as3kshj3`. Закрытый ключ остаётся на Windows. Скрипт не принимает identities/private keys.
- Snapshot, родитель state и конфигурация rclone должны быть защищены от других писателей. Один постоянный `--state-dir`, один пользователь и один host для этого remote. Не используйте несколько state directories для обхода блокировки. Не изменяйте управляемые облачные имена и staging другими программами во время операции: rclone 1.60.1 не предоставляет условное удаление по revision. Проверка ID/hash перед удалением не устраняет гонку с внешним writer между проверкой и API delete.
- State размещается вне snapshot и исходных HTML/SQLite, вне web root, на приватном диске. POSIX: владелец — запускающий пользователь, каталоги 0700, файлы 0600; symlinks/junctions и hardlinks state/ciphertext запрещены. Родитель должен существовать и не быть доступен посторонним для записи. Windows требует соответствующих ACL; защита от конкурентной подмены родителей слабее POSIX.

Конфигурация rclone читается самим rclone обычным способом, включая `RCLONE_CONFIG`/`RCLONE_CONFIG_PASS`, если они уже используются. Остальные `RCLONE_*` настройки окружения исключаются из дочерних процессов. Конфигурация и токены не печатаются и не попадают в архив. Обычное обновление OAuth token самим rclone возможно. Не запускайте инструмент под оболочкой с записью секретов/debug trace.

## Безопасный запуск

Пример для оператора после review/merge и переноса проверенных административных файлов; эти команды не являются deployment:

```sh
umask 077
/usr/bin/python3 -I -S -B /home/ubuntu/tdb-admin/offsite_backup.py \
  --backup /home/ubuntu/tdb-backups/first-snapshot \
  --state-dir /home/ubuntu/tdb-offsite \
  --remote tdb-dropbox:TCD-Backups \
  --max-archives 3 --budget-bytes 1500000000 \
  --account-reserve-bytes 300000000 \
  --local-reserve-bytes 10737418240 --timeout-seconds 1800
```

Замените путь backup на фактический завершённый каталог. Default local reserve — 1 ГиБ; пример оставляет 10 ГиБ для работающего бота на общем filesystem. Настройте reserve относительно эксплуатационных потребностей. `--recipient`, `--max-archives`, `--budget-bytes`, `--account-reserve-bytes`, `--local-reserve-bytes`, `--timeout-seconds` и `--go-memory-mib` настраиваются явно.

Последовательность: verify snapshot → проверка версий/backend/quota → потоковое шифрование → расчёт SHA-256 и Dropbox hash → повторная проверка места и dry-run → upload под уникальным staging-именем → server-side Move в `tdb-v1-<UTC дата>-<UUID>.tar.gz.age` → **полное скачивание и побайтовое сравнение** через `rclone check --download` → запись результата в приватный журнал → ротация.

Перед upload учитываются **все** файлы TCD-каталога рекурсивно, включая `first-snapshot.tar.gz.age`, посторонние файлы и остатки незавершённых отправок. Старые плюс новый должны одновременно помещаться в бюджет 1 500 000 000 байт, оставляя аккаунту минимум 300 000 000 байт. При нехватке места — отказ без предварительного удаления. Максимум 3 относится к управляемым проверенным архивам **после** ротации; временно может быть 4.

Ротация использует только собственные ранее проверенные job journals и совпадающие Dropbox ID, размер, hash и ModTime. Совпадение шаблона имени не даёт права удаления. `first-snapshot.tar.gz.age` и любые неизвестные файлы автоматически не удаляются. Новый проверенный архив всегда сохраняется, в том числе при ошибке ротации. `sync`, массовое удаление и локальное удаление ciphertext не используются.

Совместимость сверена с tagged исходниками: [Dropbox rclone 1.60.1](https://github.com/rclone/rclone/blob/v1.60.1/backend/dropbox/dropbox.go), [Move/ignore-existing](https://github.com/rclone/rclone/blob/v1.60.1/fs/operations/operations.go), [check --download](https://github.com/rclone/rclone/blob/v1.60.1/cmd/check/check.go), [age 1.1.1](https://github.com/FiloSottile/age/blob/v1.1.1/cmd/age/age.go). Dropbox upload этой версии использует overwrite internally: поэтому имена случайные, upload идёт в отдельный staging с `--ignore-existing`, а публикация — через Dropbox Move без замены назначения. Исключительное использование управляемых имён обязательно; защиты от привилегированного или конкурентного внешнего writer нет.

## Успешность и ошибки

Успех — **exit 0** и JSON `status="ok", cloud_verified=true` с `id`, `archive`, `sha256`, `bytes`. Сохраните этот небольшой результат в доверенном месте отдельно от облачной копии. Наличие файла в Dropbox или локального ciphertext само по себе не означает успех. Ошибка ротации также даёт ненулевой exit, даже если новая копия уже проверена.

| Ситуация | Действие |
| --- | --- |
| Повреждённый/изменяющийся snapshot | Проверить его существующей командой verify; подготовить новый согласованный snapshot. Не редактировать manifest или production ради обхода ошибки. |
| Недостаток локального/облачного места, неизвестная quota, отказ авторизации | Освободить место вручную вне сохраняемых данных либо исправить доступ обычным способом; не обходить reserve и не удалять последнюю хорошую копию. |
| Сеть, timeout, ошибка upload/Move/check | Сохранить state и ciphertext. После устранения причины повторить те же параметры с `--resume <id>` из безопасного сообщения об ошибке/job directory. Не начинать слепо новую отправку. |
| Resume находит полный staging/готовый файл | Проверяются ciphertext и облачная идентичность; повторное шифрование не выполняется. Проверка готового файла скачиванием выполняется снова. |
| Staging отсутствует после начатого upload, частичный/подменённый файл, конфликт имён | Безопасный отказ: неопределённый результат автоматически не перезаписывается и не удаляется. Нужен ручной разбор конкретного job и Dropbox объекта. Не править journal для «успеха». |
| Сбой во время packing | Облако не изменялось. Приватный частичный ciphertext остаётся для проверки; такой job не возобновляется. Можно начать новый запуск после проверки места. |
| Ошибка удаления старой версии | Новая проверенная копия остаётся. Resume нового job повторит полную проверку и завершит ротацию, если идентичность файлов сохранилась. |
| Другой экземпляр | Дождаться его завершения. Не удалять/подменять `offsite.lock`. |

State — долговременный журнал владения, не кеш. Потеря state делает прежние архивы неуправляемыми; права удаления не восстанавливаются по именам. Зашифрованные локальные файлы сохраняются после успеха и ошибок; проверяйте место. После самостоятельной проверки облачного восстановления можно вручную убрать ненужные локальные payload, сохраняя `job.json`; resume без локального ciphertext уже невозможен. Ограничение журнала — 1000 jobs; дальнейшая очистка исключительно вручную после разбора pruned/неудачных jobs. Скрипт не удаляет исходный snapshot.

Дочерние процессы запускаются без shell, строго по одному: Python+age либо Python+rclone. HTML читаются блоками до 512 КиБ; метаданные ограничены. Rclone: один transfer/checker, chunk 4 МиБ, buffer 1 МиБ, batch off, multithread off; Go `GOMAXPROCS=1`, `GOGC=50`, soft memory limit по умолчанию 96 МиБ (`--go-memory-mib 32..256`). Это не жёсткий RSS limit и не измерение потребления на Oracle. Общий deadline, network timeouts, ограниченные retries и контроль диска завершают процессы при сбое; stdin/stdout обрабатываются потоково, stderr подавлен, сырые ошибки API не выводятся. SIGINT/SIGTERM отменяют работу; POSIX children наследуют lock FD, чтобы SIGKILL родителя не открыл второй запуск до их завершения. Зависший filesystem syscall может задержать завершение.

## Независимая проверка восстановления

Выполняется отдельно, предпочтительно на Windows с закрытым ключом. Oracle ключ не получает.

1. Выберите точное `archive` из успешного доверенного результата. Скачайте только этот файл существующим rclone в новый приватный каталог, например `rclone copyto "tdb-dropbox:TCD-Backups/<archive>" "C:\TCD-Restore\<archive>" --ignore-existing --immutable --transfers 1`. Проверьте заранее, что назначения нет; не используйте `sync`.
2. Сравните `Get-FileHash -Algorithm SHA256` с сохранённым **доверенным** `sha256`. Публичный age recipient сам по себе не подтверждает автора: зашифровать на него может любой.
3. Только на Windows расшифруйте через `age --decrypt --identity <локальный закрытый ключ> --output <новый snapshot.tar.gz> <archive>`. Файл output обязан отсутствовать (age может перезаписать существующий). Не передавайте ключ или его содержимое в Oracle/логи.
4. Распакуйте в **новый приватный пустой каталог** с Python 3.12+ `tarfile` и `filter='data'` (ограничивает опасные tar members). Например, после создания нового пустого каталога:

   ```python
   from pathlib import Path
   import tarfile
   target = Path(r"C:\TCD-Restore\unpacked-new")
   target.mkdir(exist_ok=False)
   with tarfile.open(r"C:\TCD-Restore\snapshot.tar.gz", "r:gz") as archive:
       archive.extractall(target, filter="data")
   ```

5. Выполните существующий `backup_restore.py verify --backup <unpacked-new/snapshot>`, затем `restore --backup <.../snapshot> --destination <другой новый каталог>`, затем `verify --backup <restored>`. Синтаксис и ограничения — в [backup/restore](backup-restore.md). Абсолютные production references в SQLite сохраняются как метаданные; бот на этих каталогах не запускать. Независимую проверку на реальных данных считать завершённой только после этих действий, а не после unit tests или cloud comparison.

Уменьшение объёма за счёт исключения повторных результатов одного VOD — отдельная будущая задача. Потребуется исследовать связи SQLite/HTML, актуальность и различия результатов и сохранение истории. Этот инструмент сохраняет полный `tdb-backup-v1` совместимым с существующим восстановлением, без дедупликации и удаления результатов/истории.

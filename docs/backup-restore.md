# Административный backup/restore

`tools/backup_restore.py` — самостоятельный инструмент Python 3.12+ со стандартной библиотекой. Он не импортирует приложение, не читает `.env`, не запускает Telegram/Twitch, не управляет systemd и не меняет исходные данные. Путь каждого источника и результата задаётся явно и абсолютно. Новые зависимости, миграции, расписания и сервисы не нужны.

## Гарантия согласованности и maintenance window

Поддерживается **только backup при остановленной службе**, без других писателей в SQLite/HTML и без рестартов/deployment до завершения команды. `--maintenance-stopped` подтверждает это условие; инструмент дополнительно проверяет `tdb.service` через read-only `systemctl show` до инвентаризации, перед копированием и перед завершением: loaded, inactive/dead, MainPID=0, без ожидающего job. Работающая, failed или отсутствующая служба вызывает отказ. Флаг не является механизмом остановки или блокировкой будущего запуска: maintenance обязан обеспечить оператор. Проверки до/после не заменяют это условие.

SQLite snapshot сам по себе не защищает связанные HTML от cleanup. Поэтому online backup всего комплекта намеренно не поддерживается. Нельзя запускать эту команду параллельно с ручным cleanup, другим writer, deployment или новым экземпляром бота. Источники и приватные каталоги копий должны быть защищены от других писателей; инструмент не защищает от привилегированного процесса, который намеренно подменяет файлы во время работы.

На остановленном источнике инструмент сначала потоково клонирует `.db` вместе с существующими `-wal` и `-journal` в новый приватный staging. SQLite открывает **только этот клон**, восстанавливает журналы там и создаёт итоговую `database.sqlite3` через `Connection.backup()`. `-shm` проверяется на неизменность, но не переносится: SQLite перестраивает временный WAL index в staging. Даже создание SHM или hot-journal recovery не затрагивает production. Источник никогда не открывается через SQLite API. Staging удаляется только после успешного копирования и проверок; исходные файлы не удаляются.

Подтверждение механизмов: [SQLite Backup API](https://www.sqlite.org/backup.html), [SQLite WAL и WAL index](https://www.sqlite.org/wal.html). Обычное копирование активного `.db` и `immutable=1` для живой БД здесь не используются.

## Формат и проверки

Это обычный приватный каталог, не tar/zip:

```text
snapshot/
  database.sqlite3
  html/0/chat_<uuid>.html
  html/0/.chat_<uuid>.html.<uuid>.tmp
  html/0/.tdb-delete-<uuid>-<uuid>/page.html
  html/1/...                         # если указан второй HTML root
  manifest.json
  COMPLETE                          # SHA-256 manifest, записывается последним
```

Сохраняются все соответствующие грамматике бота HTML в явно разрешённых roots: прежние поколения, текущие и неизвестные готовые UUID-файлы, HTML temps и quarantine, включая пустые quarantine directories после unlink. Порядок roots задаёт `html/0`, `html/1` и т. д. Другие файлы, `.env`, ключи, код, spool/leases и конфигурации не копируются. Неподдерживаемые имена и внешние/unverified ссылки остаются метаданными БД, не загружаются из сети. При ready HTML за пределами разрешённых roots либо отсутствии требуемого HTML — отказ, включая старые поколения. Не создавайте или удаляйте production-файлы ради обхода этого отказа.

БД сохраняется полностью: cache/history, все поколения, current pointers, deletion journal, tombstones. Поддерживается текущая registry-схема; инструмент не мигрирует старую/неизвестную БД. Токены из окружения и конфигурации не читаются и не добавляются. Сама копия содержит приватные пользовательские данные и исходные абсолютные пути; редактирование/очистка содержимого чатов или БД не производится.

Каждый файл имеет размер и SHA-256 в manifest. Проверяются checksum manifest, точный список членов, SQLite integrity/foreign keys, current/cache consistency и size/hash зарегистрированных ready HTML. Незавершённое удаление допускает отсутствие final HTML только при сохранённом quarantine/page либо подтверждённом journal состоянии после unlink. Оно не завершается автоматически. Файловые identity из manifest относятся к исходнику и сверяются с deletion journal; новые inode не выдаются за исходные.

Источники повторно проверяются по составу, identity, размеру, временам и hashes перед записью `COMPLETE`. Изменения, неподдерживаемые symlinks/junctions, path traversal, дефицит места и timeout вызывают отказ. На POSIX чтение привязано к directory descriptors с `O_NOFOLLOW` на каждом компоненте. На Windows проверяются symlinks/junctions и identities, но это не эквивалент POSIX-защиты от конкурентной подмены родителей. Для Oracle требуется отдельная Linux qualification.

Каталог назначения создаётся эксклюзивно; существующий файл или каталог, даже пустой, не переиспользуется. Родитель должен уже существовать. Каталоги создаются 0700, файлы 0600 на POSIX; на Windows нужны соответствующие ACL. Копии не размещать в web root. Ошибочный/прерванный каталог остаётся приватным для расследования, не перезаписывается и не считается backup. Нет автоматического удаления старых или неудачных копий.

HTML читается блоками до 512 КиБ. Manifest ограничен 8 МиБ, общий инвентарь создания — 20 000 файлов/каталогов, roots — 16. Метаданные хранятся в памяти, HTML целиком — нет. Начальная оценка места учитывает HTML, staging, новую SQLite и manifest; во время копирования контролируются reserve и timeout. Дополнительная запись другими процессами всё равно может привести к ENOSPC — это безопасный отказ, а не продолжение с частичной копией. Timeout кооперативный: он не может прервать зависший filesystem syscall.

SHA-256 обнаруживает повреждение, но не является цифровой подписью или шифрованием. Защита доступа и доверенный перенос обязательны.

## Первый backup Oracle — выполняет владелец, не автоматически

1. Перенесите **проверенную версию только `tools/backup_restore.py`** в приватный административный каталог, например `/home/ubuntu/tdb-admin/backup_restore.py`, своим существующим доверенным SSH-доступом. Никакой `.env` или перенос credentials не нужен. До merge/review PR это не production-процедура. Код checkout/CI ради этого обновлять не требуется.
2. Уточните все HTML roots из действующей установки, действующий cleanup target, свободное место и inodes. Подтверждённые исходные пути: `/home/ubuntu/twitch-downloader-bot/vod_history.db` и `/var/www/tdb/html`. Если registry содержит другие managed roots, каждый существующий корень нужно явно указать ещё одним `--html-root`; не доверяйте произвольным путям из ошибочной БД.
3. Согласуйте окно без активной работы и параллельного deployment. Через обычную административную сессию **штатно** остановите `tdb.service` и дождитесь `inactive/dead`, MainPID=0. Не используйте SIGKILL, не запускайте второй бот. Штатная остановка должна дождаться owned workers и cleanup; длительность зависит от текущей задачи.
4. Создайте приватный родитель для копий и запустите инструмент от владельца данных. Следующие команды — инструкция, не выполняются самим инструментом:

```sh
umask 077
install -d -m 700 /home/ubuntu/tdb-backups
/usr/bin/python3 -I -S -B /home/ubuntu/tdb-admin/backup_restore.py backup \
  --database /home/ubuntu/twitch-downloader-bot/vod_history.db \
  --html-root /var/www/tdb/html \
  --destination /home/ubuntu/tdb-backups/first-snapshot \
  --service tdb.service --maintenance-stopped \
  --reserve-bytes 10737418240 --timeout-seconds 300
```

Здесь оставляется 10 ГиБ свободного места. Это запас для текущих известных объёмов (БД 120 КиБ, HTML около 13,6 МБ, диск около 38,8 ГиБ свободно), а не утверждение о действующих настройках. Reserve должен быть не ниже фактического cleanup target плюс операционный запас, если данные/копия находятся на одном filesystem. Default инструмента — 1 ГиБ, для Oracle используйте явный подходящий reserve.

Успех — exit 0 и JSON `status=ok`; выводятся только команда, формат, число файлов и сумма bytes. При повторе обязательно новое имя destination. Если команда отказала, изучите причину и место на диске; не удаляйте source/WAL/HTML и не подменяйте snapshot. Возобновление службы после проверки оставшегося места — отдельное действие оператора, инструмент его не выполняет. Наличие только каталога/`COMPLETE` не заменяет verify и независимую restore-проверку.

## Проверка и независимое восстановление

```sh
/usr/bin/python3 -I -S -B /home/ubuntu/tdb-admin/backup_restore.py verify \
  --backup /home/ubuntu/tdb-backups/first-snapshot
umask 077
install -d -m 700 /home/ubuntu/tdb-restore-checks
/usr/bin/python3 -I -S -B /home/ubuntu/tdb-admin/backup_restore.py restore \
  --backup /home/ubuntu/tdb-backups/first-snapshot \
  --destination /home/ubuntu/tdb-restore-checks/first-check \
  --reserve-bytes 10737418240
/usr/bin/python3 -I -S -B /home/ubuntu/tdb-admin/backup_restore.py verify \
  --backup /home/ubuntu/tdb-restore-checks/first-check
```

Restore проверяет вход до создания результата и копирует **только в новый каталог**, не использует original paths как destinations, не извлекает архив и не подключается к production. Все checks повторяются на восстановленной копии. Сбой оставляет отдельный неполный результат, не заменяет существующие данные. Ни verify, ни restore не требуют systemd или секретного окружения и могут выполняться на отдельной машине с Python 3.12+.

**Это проверка восстановимости данных, не автоматический запуск бота из копии.** Абсолютные root/reference/lease paths и deletion inode/device proof в SQLite сохраняются без переписывания. Приложение нельзя запускать на этом каталоге без отдельного плана переезда/rebinding, особенно при незавершённых удалениях. Инструмент намеренно не меняет persistent semantics и не запускает recovery/migrations/cleanup. Восстановление поверх production не предусмотрено.

## Вывод за пределы VM

На доверенной машине владельца, заменив `ORACLE_HOST` своим уже проверенным SSH-host/alias:

```sh
umask 077
scp -rp ubuntu@ORACLE_HOST:/home/ubuntu/tdb-backups/first-snapshot ./first-snapshot
```

Не переносите `.env`, SSH keys или весь checkout. Пользуйтесь существующей проверкой host key, не отключайте её и не вставляйте пароли/токены в URL или команды. Защитите локальный каталог доступом только владельца/ACL. После переноса выполните `verify`, `restore` в новый локальный каталог и повторный `verify` с той же проверенной версией инструмента. Не удаляйте единственную VM-копию до независимой успешной проверки. Автоматическое шифрование, загрузка в облако и retention не реализованы.

Синтетические тесты не доказывают наличие проверенного production backup. Первый реальный backup считается проверенным только после выполнения и независимой проверки восстановленного комплекта владельцем. Linux/Python 3.12, реальные права, directory fsync и symlink-сценарии необходимо проверить в изолированной Linux-среде до первого production применения; нагрузочные проверки для этого не нужны.
